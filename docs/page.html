The branch page

A project's web page, what its marks mean, and embedding it in your own app.

The daemon serves each project's page at http://127.0.0.1:27390/p/<id> (its id being its session's name; Several projects), and a list of every project at http://127.0.0.1:27390, with ☰ on a project's page going back to it. A project's page shows the same list as the Stream Deck keys, with a button on each branch that switches to it, and a Pull button. It's a Hologram page: the watcher pushes every change to it, so it follows a switch step by step without reloading.

The header

  • ☰ goes to the list of every project, and the project's name (the config's name).
  • On branch: the branch checked out now. Its row in the list is tinted too.
  • The webhook's state: webhook on, webhook connecting, webhook lost (with why), or webhook off: run clawswap smee when no channel is set.
  • Pull, with how many new commits the checkout's branch has on origin ("↓ Pull 3 new commits", or "up to date"). While a pull runs it shows the step it's on.
  • Connect Stream Deck, in Chrome or Edge: drives a Stream Deck from this page over WebHID, without OpenDeck. See Stream Deck.
  • ⚙ opens the config editor in a new window.

Walkthroughs

When the checkout has walkthroughs, a row of ▶ buttons under the header runs them in Chrome on this machine. The ones the branch added come first, outlined, and the line below follows the one running.

Merge-status marks

Each row starts with a mark for its merge status, as bmx's branch menu shows it. Hover it for what it means.

  • ⎇ The base branch, the one the others merge into.
  • ✓ Merged into the base: every commit of the branch is already in origin's base branch.
  • ● An open pull request, not merged yet.
  • ◌ A draft pull request, not merged yet.
  • ○ Not merged, and no open PR (or no GitHub token to ask with).

Then the PR's number and title (or the branch's short name), and its status on the right.

Row status

The coloured edge on the left of a row, and the text on its right:

  • Current: the checkout's branch (Uncommitted if tracked files have changes).
  • New commits: the checkout's branch has commits on GitHub it doesn't have. Pull to get them.
  • A spinner and a step's label: a switch to this branch is running, on that step. The spinner shows the moment you click the row (or press its Stream Deck key with this page open), on Switching, then Fetching while clawswap looks at origin, then each step. The Pull button spins the same way.
  • Failed: the last switch to this branch failed; the error shows above the list.

The base branch, pinned first

The base branch is always the first row, whatever its commit date. The rest follow newest commit first. The base is the config's base, else origin's default branch (what origin/HEAD points at), else main or master, whichever origin has. CLAWSWAP_BASE overrides it for one run. The ✓ marks are worked out against it, so set base if your PRs merge into something other than the default branch.

Narrow layout

Below 480 px wide the page lays itself out as a compact list, like a dropdown menu: tight rows, the current one tinted, the status under the title. That's the width it gets in an app's menu (below). It follows your system's light or dark theme.

Embedding it in your app

Your app's dev page can show clawswap two ways: frame the watcher's page, or build its own control on the API. Use both: the page for switching, and a Pull button of your own beside it. The examples/react-embed Vite + React app does both. (It's a test target, so it's JavaScript; clawswap itself isn't.)

The recommended setup

Put three things in your app's dev chrome (a top bar, or a sidebar's bottom):

  1. A Branches button that opens the page in a dropdown (below).
  2. A Pull button next to it, on the API (below), so pulling the branch you're on is one click, without opening the menu, and the button shows when there's something to pull.
  3. A listener that reloads your page when a switch or pull is done, however it was started (below: it follows the API's /events stream), unless your dev server reloads it already.

The debug panel in a sidebar is optional, for projects with walkthroughs.

The page in an iframe

The simplest: a button in your top bar that opens a dropdown with the page in it.

<iframe src="http://localhost:27390/p/myapp" title="clawswap"></iframe>

where myapp is the project's id (its session's name, in lower case).

The example's BranchMenu loads the frame with your page and only hides it while the menu is closed, so it follows a switch whether the menu is open or not, and tells clawswap when your tab comes into view (Focus, below). It adds reload, open-in-a-tab and close buttons. Things to know:

  • Framing. Neither clawswap's endpoint nor Hologram sets X-Frame-Options or frame-ancestors, so the page frames.
  • Use localhost for both. Hologram's session cookie is SameSite=Lax. localhost:27391 and localhost:27390 are the same site (ports don't count), so the framed page gets its cookie. Mixing localhost and 127.0.0.1 makes them cross-site.
  • Restarts. A switch kills your dev server, while the framed page keeps its own connection to the watcher and follows the switch to the end. Whether your app's page reloads is up to it: see below.
  • Focus. The framed page tells the daemon when its tab comes into view, so the Stream Deck keys that follow the selected project, and tools that follow the focused project, show the project you're looking at. It can only while it's loaded, so load the frame with your page and hide it, rather than adding it when the menu first opens. An app with no frame at all can put this in its dev layout instead: 
    <script src="http://localhost:27390/clawswap-focus.js" data-project="myapp" defer></script>

Reloading your app after a switch

clawswap doesn't reload your app's page: it's on another port, so another origin, and can't. A Vite app reloads by itself when its dev server comes back. Anything else (a Phoenix app, a plain server) stays on the old page, so give it a listener in its dev JavaScript (Phoenix: assets/js/app.js) that follows the project's GET /p/<id>/events. That's a Server-Sent Events stream of the project's state: once when it opens, then each time the state changes. It hears every switch and pull however it was started (the page, a Stream Deck key, the CLI or the API), with no frame open:

const CLAWSWAP = "http://localhost:27390/p/myapp";
let doneAt; // the last finished switch's, once known

new EventSource(`${CLAWSWAP}/events`).onmessage = (e) => {
  const next = JSON.parse(e.data).switch?.doneAt ?? null;
  if (doneAt !== undefined && next !== null && next !== doneAt) return location.reload();
  if (doneAt === undefined || next !== null) doneAt = next;
};

Things to get right:

  • Reload on a new doneAt only. switch.doneAt is set when a switch or pull is done and its servers listen on their ports again. A switch that starts drops it until then, so don't reload on it going away: the page would load while your server is down, and the browser's error page doesn't reload again. The first event only says where things stand (a switch done before the page loaded isn't news). A failed switch, or a pull with nothing new, sets no doneAt.
  • Reconnects are free. EventSource opens the stream again by itself when the daemon restarts, and the first event after that is the state then. It gives up on an answer that isn't a stream: a 404 for a project that isn't running (or a clawswap older than /events). Poll GET /p/<id>/state every few seconds then, with the same doneAt rule, and try the stream again later.
  • Origins. The browser may call the API from your servers' own localhost ports; add others with the config's origins. Use the config's port if it isn't 27390.

The page in a frame also tells its parent when a switch or pull is done, whoever started it:

{ clawswap: "switched", branch: "claude/fix-login" }
addEventListener("message", (e) => {
  if (e.origin === "http://localhost:27390" && e.data?.clawswap === "switched") location.reload();
});

That's enough on its own only while the frame is loaded: load it with the page and hide it rather than remove it when the menu closes, as the example's BranchMenu does. A frame that's only added when the menu first opens misses a switch from a key or the CLI after each reload until the menu is opened again, so listen on /events too. The origin is the daemon's, without the /p/<id>.

A Pull button

The page has Pull, but it's only reachable once the menu is open. Give your app its own button next to Branches: POST /p/<id>/pull pulls the checkout's branch, and the state's upstream.behind says how many commits there are to pull. With no framed page to post switched, the same /events stream drives the button and the reload (above), so this one listener does both. In plain JavaScript:

<button id="clawswap-pull">↓ Pull</button>

const CLAWSWAP = "http://localhost:27390/p/myapp";
const button = document.getElementById("clawswap-pull");
let doneAt; // the last switch's, once known

// EventSource reconnects by itself when the daemon restarts.
new EventSource(`${CLAWSWAP}/events`).onmessage = (e) => {
  const state = JSON.parse(e.data);
  const run = state.switch, behind = state.upstream?.behind;
  const next = run?.doneAt ?? null; // gone while a switch runs, so only a new time counts
  if (doneAt !== undefined && next !== null && next !== doneAt) return location.reload();
  if (doneAt === undefined || next !== null) doneAt = next;
  const running = run?.phase === "running";
  button.disabled = running;
  button.textContent = running ? `Pulling: ${run.step || "…"}`
    : behind ? `↓ Pull ${behind} new` : "↓ Pull";
};

button.onclick = () => fetch(`${CLAWSWAP}/pull`, {
  method: "POST", headers: { "Content-Type": "application/json" }, body: "{}"
});

The browser can call the API from your server's own localhost port (it's an allowed origin; add others with origins). A pull with nothing new answers 202 with "Already up to date" in switch.notes and changes nothing. The example's BranchBadge (below) does the same in React, polling /state instead.

The debug panel in a sidebar

The debug panel is on its own at /p/<id>/panel, filling the page at any width and without its 🐞 (your app opens and closes its sidebar). Frame it in a sidebar on the right of your app:

<iframe src="http://localhost:27390/p/myapp/panel" title="clawswap debug panel"></iframe>

The same framing notes apply. A page served cross-origin isolated (Cross-Origin-Embedder-Policy: require-corp) needs the frame credentialless (Chromium). Leave the sidebar out when navigator.webdriver is true, so a Chrome the panel or a walkthrough drives shows your app without it.

Your own control on the API

The example's BranchBadge shows the checkout's branch as a picker, Pull with how far behind it is, and the step a switch is on, from the project's GET /p/<id>/state, POST /p/<id>/switch and POST /p/<id>/pull. Its useClawswap hook polls /state every 2 s while a switch runs and every 10 s otherwise, and treats failed fetches during a switch as expected (its own server is restarting). The browser can call the API because a server's own localhost port is an allowed origin; add others with origins.

Try the example

clawswap needs a repo with branches on a remote, so give the example one of its own. From your clawswap clone:

cp -r examples/react-embed ../react-embed && cd ../react-embed
git init -b main && git add . && git commit -m "react-embed"
gh repo create react-embed --private --source . --push   # or any remote
clawswap up

Open http://localhost:27391, push a branch that changes src/App.jsx (or adds a dependency), and switch to it from the Branches menu or the badge. Set VITE_CLAWSWAP_URL in .env.local when the config's port isn't 27390, or its session isn't react-embed (VITE_CLAWSWAP_URL=http://localhost:27390/p/<id>).

Walkthroughs

Short scripts on a branch that drive a browser through its change, so you watch the feature instead of clicking through it yourself.

When Claude pushes a branch, it can push a walkthrough with it: an Elixir script in the project's walkthroughs/ folder that opens your app, says what it's about to show, and clicks, types and checks its way through the change. Switch to the branch, press its ▶ on the branch page, and Chrome opens on your machine and plays it: slowed down, with a caption for each part and the element it's about to click outlined. The page follows along and says whether it ran to the end, or where it stopped.

# walkthroughs/badge-pull.exs
say "The badge now shows how far behind the branch is"
visit url(:web)
see css(".badge button", text: "Pull")

say "Open the Branches menu: clawswap's page, in an iframe"
click "Branches"
in_frame "iframe[title=clawswap]", fn ->
  see "Current"
end

say "Rename the project in the settings"
visit url(:clawswap, "/settings")
fill_in "the repo folder's name", with: "demo"
click button("Save")
see "Saved."

Running one

  • From the page. The branch page lists the checkout's walkthroughs under the header. Those the branch added or changed since it left the base branch come first, outlined in blue. ▶ runs one in the watcher, so the browser opens on the machine running clawswap. The line below the buttons shows the caption it's on, then ran to the end or what failed.
  • From the terminal. In your project's repo, with the session up: 
    clawswap walk                  # the walkthroughs this branch added or changed
clawswap walk badge-pull       # one by name (or several)
clawswap walk --headless       # without a window, to check one passes
    It exits 1 when one fails, saying where.
  • API. POST /walk {"name": "badge-pull"}, then follow walk in /state; see API.

A failure names the line, the caption it was showing and what it couldn't find, and saves a screenshot of that moment in the temp folder (its path is in the message).

What it needs

  • Chrome and chromedriver of the same version. clawswap drives Chrome through chromedriver (with Wallaby). Install chromedriver from your package manager, or take the build matching your Chrome from Chrome for Testing. If they aren't on your PATH as chromedriver and google-chrome (or chromium), set CLAWSWAP_CHROMEDRIVER and CLAWSWAP_CHROME to their paths, in the shell you run clawswap up from.
  • The servers running. A walkthrough drives your app as the session runs it.
  • A display. On Linux without DISPLAY or WAYLAND_DISPLAY (a CI runner, Claude's cloud session) it runs headless by itself.
VariableWhat it does
CLAWSWAP_HEADLESS1 runs without a window, 0 with one, whatever else says.
CLAWSWAP_SLOWMilliseconds to wait before each action (twice that on a caption). 600 with a window, 0 without.
CLAWSWAP_WAITHow long a command waits for what it looks for, in ms. 10000.
CLAWSWAP_CHROME, CLAWSWAP_CHROMEDRIVERThe binaries' paths.

The folder is walkthroughs next to the config; set walkthroughs: in the config for another.

Writing one

A walkthrough is Elixir, evaluated with these commands imported. Each waits for what it looks for (10 s, or timeout: ms) and fails the walkthrough when it doesn't turn up. A string finds a button, link, label or similar by its visible text; where that isn't precise enough, pass a query.

CommandWhat it does
say "text"Shows a caption at the bottom of the page, and pauses on it. Each caption is a step: the page and the terminal follow them, and a failure says which one it was in.
visit urlOpens a page: a full URL, or a path on your first server with a port.
url(:web, "/path")A server's address by its name in the config (url(): the first with a port; url(:clawswap): the branch page).
click "text" / click queryClicks it, after outlining it.
fill_in "field", with: "text"Types into a field found by label, id, name or placeholder, then leaves it (so change events fire).
choose "select", "option"Picks an option in a select found by label, id or name (or a query).
press [:escape]Sends keys: strings and Wallaby key atoms.
see "text" / see queryWaits until the page shows it. refute_see waits until it's gone.
in_frame "iframe css", fn -> … endRuns the commands inside an iframe.
js("return …", args)Runs JavaScript in the page and returns its value.
before_load("js")Runs JavaScript in every page from the next load on, before the page's own: stand-ins for browser APIs (clawswap's tests fake navigator.hid this way).
wait_until(fn -> … end)Waits until the function returns something truthy.
pause(ms), screenshot("name")Waits; saves a screenshot and returns its path.
css/2, xpath/2, button/2, link/2, text_field/2, select/2, option/2Queries, as Wallaby's: css(".badge select"), css("li", text: "main"), button("Save").
session()The Wallaby session, for anything else.

Asking Claude for them

Tell Claude in your repo's CLAUDE.md, so every branch comes with one:

With each branch that changes what the app does, add walkthroughs/<short-name>.exs: a clawswap
walkthrough (https://cbishopvelti.github.io/clawswap/walkthroughs.html) that shows the change, with a
`say` caption before each part. Check it passes with `clawswap walk --headless` before pushing.

Claude's cloud sessions have no display, so clawswap walk runs headless there, and a failure's screenshot shows Claude what the page looked like.

clawswap's own browser tests

clawswap tests its page the same way: test/integration copies examples/react-embed into a repo of its own with a few branches, runs clawswap up for it in zellij and in tmux, and drives Chrome through the merge marks, the Branches menu, a switch, the config editor, the ▶ buttons and a stand-in Stream Deck. They need Chrome, chromedriver, Node.js, tmux and zellij, and are left out of mix test:

mix test.integration                                      # headless
CLAWSWAP_HEADLESS=0 CLAWSWAP_SLOW=800 mix test.integration  # watch them
tmux -L clawswap-tests attach                             # and the panes, in another terminal

They use ports 8790 and 5173, so stop your own session first.
